## 1. 背景与目标

开发者已有 C++、算法竞赛、Linux 网络编程、Reactor 服务器和 Python AI 应用经验，希望以游戏服务端求职为主，同时积累客户端开发经验，并发布具有实际使用价值的 GitHub 开源项目。

本项目将这些经验连接为一条完整链路：客户端采集操作 → C++ 服务器运行游戏规则 → 同步状态 → 自动执行测试 → 记录并解释错误现场。

目标按以下顺序排列：

1. **求职展示：**能够现场演示，并解释房间状态机、连接生命周期、逻辑帧、预测与校正、请求幂等、重连和性能瓶颈。
2. **实际用途：**让学习者运行同步实验，让开发者复用测试场景、协议思路和故障排查方法。
3. **开源传播：**通过易运行的示例、可复现问题和中英文说明降低体验门槛，获得真实使用反馈。

Star 数作为观察指标，不作为发布门槛或预期收益承诺。

## 2. 产品定义

NetArena 是一个附带 2D 多人争夺金币游戏的联机开发实验场。用户可以玩游戏、观察服务器和客户端状态、运行测试场景，并在失败时沿时间线查看证据。

AI 将自然语言测试意图转换为有限、可校验的场景配置。游戏规则、测试执行和正确性判定由程序完成。没有模型服务或 API Key 时，游戏、内置场景、测试和回放仍能使用。

首版服务对象是项目自身的示例游戏。接入其他游戏需要编写适配层，不宣称能够直接测试任意游戏。

## 3. 用户与使用场景

| 用户 | 主要需求 | 产品提供的价值 |
| --- | --- | --- |
| 开发者本人及技术面试官 | 快速理解项目并验证技术能力 | 可玩的客户端、架构说明、故障案例、实测报告 |
| 游戏网络编程学习者 | 观察同步机制在不同网络条件下的表现 | 权威状态、预测状态、显示状态及误差变化 |
| 独立开发者 | 获得测试和排查联机问题的参考实现 | 协议机器人、结构化场景、断言、运行产物 |
| 开源贡献者 | 在有限范围内增加能力 | 清晰模块边界、测试入口、贡献说明 |

核心使用场景：

- 启动服务器和两个客户端，创建房间并完成一局金币争夺。
- 对比正常网络与弱网下的角色运动，观察预测和校正的效果。
- 在断线、重连、重复请求和多人争抢条件下检查得分与实体状态。
- 运行失败场景，从结果报告进入对应时刻，查看输入、服务器事件和状态快照。
- 用自然语言生成场景，确认配置后执行，将有效场景保存为长期回归用例。

## 4. 首版玩法

采用单张固定 2D 俯视地图，支持每房间 2–4 名真人或机器人玩家。玩家移动并拾取金币，每枚金币计 1 分。

- 服务器负责移动合法性、碰撞、拾取、计分、计时和胜负判断。
- 一枚金币只能被领取一次；同一业务请求重复到达不得重复产生效果。
- 默认一局 60 秒、初始 10 枚金币，时间结束或金币全部领取后结算。
- 同分时允许并列，不增加额外决胜机制。
- 首版使用简单静态边界和障碍物，不引入复杂刚体、战斗、技能或装备。
- 测试模式允许固定出生点、金币位置和时长，使特定边界情况容易构造。

上述数值集中配置。测试产物必须记录实际使用的配置，不依赖默认值推测历史行为。

## 5. 产品组成与职责

| 组成 | 核心职责 | 边界 |
| --- | --- | --- |
| C++ 服务器 | 会话、房间、逻辑帧、规则、权威状态、校验、事件记录 | 不等待模型调用；单进程部署 |
| Godot 客户端 | 输入、画面、交互、预测、插值、校正、调试显示 | 不能自行确认得分或胜负 |
| 测试执行器与机器人 | 读取场景，通过游戏协议执行动作，检查断言 | 机器人遵守相同业务校验 |
| 记录与回放工具 | 展示事件、快照、失败位置及状态差异 | 首版重点是历史状态浏览 |
| Python AI 辅助层 | 自然语言转场景、结构校验、调用记录 | 可选组件；不自动执行任意生成代码 |

技术基线为 C++20、Godot 4.x、Python 3。具体小版本、依赖版本、序列化方式和网络库在技术设计中锁定，需求阶段不承诺多个后端同时可用。

传输层优先验证成熟 UDP 库方案。独立 C++ 服务端与 Godot 客户端使用显式定义的应用消息协议。Godot 高层 RPC 不是独立 C++ 服务器的即插即用接口；跨语言互通须在首个里程碑验证。

## 6. 范围与优先级

**P0：v0.1 发布必须具备。** P1 是首版之后的增强项；P2 是已有真实需求后再考虑的方向。

| 优先级 | 范围 |
| --- | --- |
| P0 | 单房间完整游戏；版本握手；临时身份；房间准备与结算；移动同步；预测、校正、插值；断线重连；幂等计分 |
| P0 | 规则机器人；场景配置与校验；断言；延迟和丢包实验；结构化记录；失败报告；历史快照回放 |
| P0 | 自然语言生成场景；无模型运行路径；内置回归场景；构建与测试自动化；发布包和文档 |
| P1 | 多房间调度与压力测试；带宽限制、乱序等更多故障；固定版本输入重演及状态哈希对比 |
| P1 | 更完整的客户端状态记录；AI 根据事件证据提出诊断建议；第二种测试适配器 |
| P2 | Unity/Unreal 客户端适配；跨进程扩展；复杂地图和更多玩法；社区场景库 |

首版不包含账号注册、商城、支付、持久化经济、排行榜、聊天、语音、匹配服务、NAT 穿透、开放公网运营平台、强化学习训练或通用 NPC 对话。

## 7. 首版成功标准

| 编号 | 成功标准 | 验证材料 |
| --- | --- | --- |
| PR-01 | 两名新用户按说明能连接并完成一局，四名玩家可以正常参与 | 快速开始文档、发布包、完整操作记录 |
| PR-02 | 能展示预测、插值和校正的效果，并解释弱网下的变化 | 演示视频、调试视图、场景配置 |
| PR-03 | 能自动验证金币不重复发放、重连无重复实体、旧快照不回退状态 | 场景、断言结果、回归报告 |
| PR-04 | 测试失败后能定位到具体断言、服务器逻辑帧和相关事件 | 失败产物、回放入口 |
| PR-05 | 同一保存场景可再次运行；游戏和测试不依赖模型在线 | 无模型的自动化验证记录 |
| PR-06 | 自然语言生成的场景经过校验后可执行，错误输出被明确拒绝 | 固定评测集、结构通过率和语义核对结果 |
| PR-07 | 性能结论可复测，清楚说明硬件、构建、负载和网络条件 | 实测报告、运行命令和原始结果 |

“再次运行同一场景”不等于操作系统网络调度逐帧一致，也不等于保证所有偶发错误每次复现。已知回归案例须通过固定测试条件获得稳定结果。

## 8. 展示与开源交付

发布内容包括：

1. 服务器、客户端、测试执行器和 AI 辅助模块源代码。
2. 可下载客户端及服务端启动方式；首版支持矩阵写明实际验证的平台。
3. 至少 6 个内置场景，覆盖正常流程、争抢、重复请求、重连、弱网和过期快照。
4. 三类故障案例的说明、失败证据及修复后的验证结果；演示故障只允许在测试构建中启用。
5. 中英文项目简介与快速开始，中文详细需求、架构、协议、测试及性能文档。
6. 一段 1–3 分钟演示视频：运行游戏 → 触发测试失败 → 查看现场 → 修复后验证。
7. 明确的代码许可证、第三方依赖和美术素材许可清单；不分发未经许可的资源。

首次体验目标：在列明的前置条件满足后，用户约 10 分钟内完成本地双客户端演示。下载、安装工具及模型部署耗时单独说明。

首版默认建议 Linux 运行服务端和自动化测试，Windows 与 macOS 提供客户端。发布支持仅以实际构建和冒烟验证结果为准，未验证平台不得标为已支持。

## 9. 里程碑与退出条件

按单人每周约 20–25 小时估算，首个完整展示版本预留 8–10 周；这是规划估计，需根据互通验证和客户端学习成本调整。

| 里程碑 | 参考时间 | 退出条件 |
| --- | --- | --- |
| M1 联机闭环 | 第 1–2 周 | C++ 与 Godot 协议互通；两人移动、争抢、结算；至少一次真机间连接验证 |
| M2 同步与恢复 | 第 3–4 周 | 预测、插值、校正可观察；输入校验、幂等和重连通过测试 |
| M3 测试与证据 | 第 5–6 周 | 场景机器人、断言、弱网、记录和回放形成闭环 |
| M4 AI 辅助 | 第 7–8 周 | 自然语言生成场景；校验与无模型路径完成；固定评测集有结果 |
| M5 开源发布 | 第 9–10 周 | 自动化检查、支持平台验证、性能报告、文档及视频完成 |

若进度不足，先发布标明范围的预览版，保持已有功能可靠；完整 v0.1 仍须满足全部 P0。不通过降低断言、隐瞒失败或编造性能结果完成里程碑。

## 10. 风险与处理策略

| 风险 | 影响 | 处理策略 |
| --- | --- | --- |
| 跨语言协议互通成本高 | 阻塞游戏闭环 | 首先验证连接、消息编解码和断线；仅选择一种传输方案 |
| 同步与客户端学习同时展开 | 进度不确定 | 单张 2D 地图、简单运动模型、先权威同步后加预测 |
| 误把视频式回放当成错误复现 | 演示结论失真 | 在界面和文档区分状态浏览、重新跑场景、输入重演 |
| LLM 输出不合法或误解意图 | 测试内容错误 | 有限动作与断言、Schema 校验、配置摘要、显式运行 |
| 项目逐步变成通用平台 | 单人无法完成 | P0 固定为一个示例游戏；新引擎和多房间放入后续版本 |
| 开源使用价值未经验证 | 功能做完但无人使用 | 邀请少量真实用户试跑，优先修复安装、理解和复用障碍 |

## 11. 需求管理

- 功能需求使用稳定编号 `FR-xx`，非功能需求使用 `NFR-xx`，验收场景使用 `AC-xx`。
- 变更记录应写明原因、受影响编号、验收变动和工期影响。
- 模块、主要接口和线程边界见配套模块设计；开发前继续完成具体依赖锁定、传输互通及构建验证，并登记验证结果。
- 首版功能完成的依据是对应验收条件和证据，不以代码文件存在或界面截图作为唯一依据。
