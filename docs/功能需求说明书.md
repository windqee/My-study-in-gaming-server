本文定义系统必须表现出的行为、异常处理和验收条件。除明确标记 P1 的条目外，全部为 P0。下文中的默认参数属于拟定需求，可在技术设计阶段根据验证调整，但须同步修改验收基线。

## 1. 术语与约定

| 术语 | 本文含义 |
| --- | --- |
| 权威状态 | 由服务器确认的游戏状态；客户端不能自行改变最终结果 |
| Tick | 服务器逻辑更新的编号，局内单调递增；默认 30 次/秒 |
| 输入序号 | 某玩家会话内单调递增的操作编号，用于排序和去重 |
| 预测状态 | 客户端根据尚未被服务器确认的输入估计的自身状态 |
| 显示状态 | 最终绘制的角色状态，可能经过插值或平滑处理 |
| 场景 | 预先描述参与者、动作、网络条件、断言和超时的测试配置 |
| 状态回放 | 根据已记录快照和事件查看历史，不重新执行游戏逻辑 |
| 场景重跑 | 重新执行保存的场景；实际网络时序可能与原运行不同 |
| 输入重演 | 在固定初始状态、版本及接受顺序下重新执行输入；属于 P1 |

所有时间字段须声明单位；网络延迟必须区分单向延迟和往返延迟。测试使用逻辑帧安排局内动作，使用真实时间约束连接和整体运行超时。

## 2. 全局配置基线

| 参数 | 默认值 | 约束 |
| --- | --- | --- |
| 同时活动房间数 | 1 | 多房间属于 P1；房间关闭后允许创建下一局 |
| 每房间人数 | 2–4 | 真人与机器人合计；重连保留席位计入容量 |
| 每局时长 | 60 秒 | 测试场景可覆盖 |
| 初始金币数 | 10 | 测试场景可设置位置及数量 |
| 逻辑更新频率 | 30 Hz | 由服务器决定，并写入连接信息与记录 |
| 权威快照频率 | 10 Hz | 可配置，不能用快照频率代替逻辑更新频率 |
| 客户端输入发送上限 | 30 次/秒 | 单个输入批次大小和字节上限由协议明确 |
| 无有效会话流量判定断线 | 3 秒 | 使用心跳；测试报告记录实际判定时间 |
| 重连保留时间 | 判定断线后 10 秒 | 以服务器时间为准，不可通过重试无限续期 |
| 单次测试总超时 | 120 秒 | 场景可显式覆盖；退出后清理子进程和连接 |

## 3. 连接、身份与房间

### FR-01 建立连接与协议握手

- 客户端可配置服务器地址和端口，界面区分未连接、连接中、已连接和失败。
- 握手携带协议版本；服务器返回版本、临时玩家身份及可用能力。
- 版本不兼容、服务不可达和连接超时应给出不同的可读错误。
- 协议应限制消息长度、枚举值、数组大小及字段范围；无效数据不得导致服务器崩溃。

**验收：**兼容客户端正常连接；不兼容版本在进入房间前被拒绝；超长及非法消息被拒绝并留下受限日志。

### FR-02 临时身份与连接生命周期

- 首版提供访客身份，不要求注册。显示名称不能作为身份凭证。
- 服务器生成不可预测的恢复凭证，用于恢复已存在的玩家会话。
- 每个玩家同一时刻只能有一个有效连接；重连成功后旧连接失效。
- 恢复凭证不得进入公开回放、普通日志或错误报告。
- 首版定位本地及受控网络实验，公网部署所需加密和防护不得在未经验证时宣称已具备。

**验收：**伪造身份但无有效凭证不能恢复他人状态；同一身份不会因两个连接产生两个玩家实体。

### FR-03 房间创建、加入、准备与开始

- 用户能够创建房间、通过房间标识加入，并看到成员、连接和准备状态。
- 房主在至少两人且当前成员全部准备后可发起开始，条件由服务器校验。
- 房间满员、正在运行或不存在时，加入请求被明确拒绝；运行中的有效重连除外。
- 等待阶段房主退出时，将房主转交给加入时间最早的在线成员；无人在线则关闭房间。

**验收：**1 人不能开始，2–4 人可开始，第 5 人不能加入；并发加入不会超过容量。

### FR-04 房间状态机与结算

状态流转为 `WAITING → RUNNING → FINISHED → CLOSED`，等待阶段无人时可直接进入 `CLOSED`。

- `WAITING` 接受加入、准备、取消准备和开始操作。
- `RUNNING` 由服务器驱动游戏；时间结束或金币耗尽后只结算一次。
- `FINISHED` 停止产生游戏效果，展示得分和并列情况；允许玩家退出。
- 结算界面保留最多 15 秒后关闭房间；全部成员提前退出则提前关闭。
- 一局结束后的玩家开始新局时使用新比赛标识，不沿用旧局请求去重空间。

**验收：**重复开始、重复结算以及上一局的迟到操作不能改变当前局状态；关闭后资源释放且能重新建房。

## 4. 游戏规则与状态同步

### FR-05 服务器权威移动与拾取

- 客户端提交方向或动作意图，服务器根据速度上限、地图边界、障碍和当前状态计算位置。
- 方向向量需归一或限幅；客户端上报最终坐标不能直接覆盖权威位置。
- 拾取须检查玩家是否在线、金币是否存在以及距离是否满足规则；成功后增加 1 分并移除金币。
- 同 Tick 竞争同一金币时，按稳定、公开的顺序处理：玩家 ID，再按玩家输入序号。不同 Tick 按先后处理。
- 已移除的金币不能被再次领取；同一请求重复到达不再次加分。

**验收：**越界或超速输入无效；两人争抢同一金币最多一人得分；重复请求和重新编码的新请求均不能再次领取已移除金币。

### FR-06 固定逻辑帧与输入处理

- 服务器以固定时间步长更新游戏，网络接收和模型调用不能阻塞逻辑更新。
- 输入包含比赛标识、会话标识和序号；服务器拒绝旧局、失效连接、已处理和明显越界的输入。
- 单 Tick 内接收队列及每玩家处理量必须有界。迟到输入的采纳、合并或丢弃策略在协议中固定并记录原因。
- 逻辑计算超时应记录超时次数和积压，不以无界补帧使服务器长期失去响应。

**验收：**连续输入不会改变固定步长；重复、过期和洪泛输入不能重复执行或让队列无限增长。

### FR-07 快照同步与过期保护

- 权威快照包含比赛标识、Tick、快照序号、玩家位置、得分、金币状态和相关玩家的已处理输入序号。
- 首版允许发送完整快照，差量压缩不作为发布要求。
- 客户端不能让迟到的旧快照覆盖较新的权威状态；新比赛必须重建同步上下文。
- 新加入或重连成功后先获得完整状态，再接受增量输入处理。

**验收：**有意反序投递快照时，客户端权威 Tick 不回退；重连不依赖已经错过的旧消息恢复状态。

### FR-08 预测、校正与插值

- 自身移动在本地即时预测，保留有界的未确认输入历史。
- 收到服务器确认后，移除已处理输入，在权威状态上重新应用仍有效的输入。
- 其他玩家通过快照插值显示；缓存不足时采取明确的停止或有限外推策略，不无限外推。
- 调试模式可独立关闭预测和插值，便于在同一场景中比较效果。
- 本地碰撞预测与服务器规则尽量一致；无法一致时以服务器校正为准。

**验收：**开启预测时自身操作不必等待网络往返才能显示；稳定网络恢复后位置重新收敛；未确认输入缓存达到上限时可恢复且不崩溃。

### FR-09 断线重连

- 判定断线后保留玩家身份、得分和席位 10 秒，停止处理该连接的新输入，并将持续移动意图归零。
- 玩家在有效期内恢复连接后沿用原玩家实体，接收完整快照，并清除客户端旧预测历史。
- 超过保留期释放席位并移除实体；已经结束的比赛只返回结算状态，不恢复运行。
- 若所有玩家的保留期均已结束，运行中的房间可提前关闭，记录中止原因。

**验收：**重连后得分保持、实体唯一且能继续操作；过期凭证不能恢复旧比赛；旧连接消息不再影响游戏。

## 5. 可观察性与测试系统

### FR-10 客户端调试视图

- 展示 RTT、最近快照 Tick、已确认输入序号、未确认输入数、位置校正距离和连接状态。
- 以不同标记显示自身的权威位置、预测位置和最终显示位置。
- 标明服务器仿真、网络快照与渲染三种更新频率，不混为一个 FPS。
- 测量值缺失时显示“不可用”，不以零值冒充测量结果。

**验收：**关闭预测、增加延迟或触发校正时，相应状态可观察，并可与记录中的事件核对。

### FR-11 规则机器人

- 机器人通过与真人相同的业务协议连接，接受相同规则校验。
- 支持连接、加入、准备、开始、移动、拾取、等待、断开、重连和重试请求。
- 机器人支持固定动作序列，首版无需寻路学习或强化学习训练。
- 测试执行器可编排房间配置和网络条件，但不能借此让机器人绕过拾取等业务规则。

**验收：**2–4 个机器人可以独立完成一局；非法机器人请求与非法真人请求被一致处理。

### FR-12 结构化场景与执行

- 场景使用版本化 JSON，包含名称、初始配置、玩家、动作、网络设置、断言及总超时。
- 动作使用有限枚举；所有引用的玩家、目标和时间字段在执行前校验。
- 局内动作可按 Tick 安排；连接相关操作有单独的超时与前置条件。
- 执行结果明确区分 `PASS`、`FAIL`、`ERROR` 和 `TIMEOUT`：断言失败属于 FAIL，启动或环境故障属于 ERROR。
- 无效配置不能启动游戏进程；测试结束或被取消后清理自身创建的进程、连接和临时网络规则。

**验收：**同一保存场景可以反复执行；缺字段、未知动作、非法范围或不存在引用被定位到具体字段；退出不遗留测试进程。

### FR-13 程序断言与失败证据

首版至少支持：

- 指定金币的成功领取事件总数不超过 1。
- 指定玩家的得分等于期望值。
- 房间中的指定玩家实体数量等于 1 或 0。
- 重连后客户端获得指定比赛的完整权威快照。
- 客户端已应用的权威快照序号不回退。
- 在限定时间或 Tick 内完成预期状态变化。

断言读取结构化事件或状态，不依赖模型判断。客户端状态相关断言使用带来源标记的客户端遥测，不以服务器状态代替客户端状态。

**验收：**失败报告包含断言编号、期望值、实际值、关联玩家及 Tick；缺失遥测应报 ERROR 或超时，不得视为通过。

### FR-14 弱网与故障注入

- 首版支持固定延迟及随机丢包，能够指定方向、作用连接和生效区间。
- 若声明为网络丢包，注入点应位于传输可靠性机制之外，使可靠传输能真实处理丢包；不可在业务层丢消息后标为真实 UDP 丢包。
- 业务层重复请求、旧快照投递等作为单独故障类型，标明注入层级。
- 记录注入配置、随机种子和实际故障事件；种子不作为全系统确定性的保证。
- 若平台不支持某种注入方式，明确报不支持，不能静默按正常网络运行。

**验收：**正常、双向各增加 75 ms 单向延迟、双向各 3% 丢包三种配置可运行；报告区分注入参数与实测 RTT。测试仅作用于自身启动的连接或隔离环境，不修改机器全局网络状态。

## 6. 记录、回放与报告

### FR-15 结构化运行记录

每次运行创建独立目录，建议包含：

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | 运行 ID、时间、构建版本、协议和场景版本、实际配置、环境信息 |
| `scenario.json` | 本次执行的完整场景，不包含模型密钥 |
| `events.ndjson` | 连接、输入接受/拒绝、拾取、得分、故障、断言等事件 |
| `snapshots.ndjson` | 权威快照及必要的客户端遥测，标注来源和 Tick |
| `summary.json` | 结果分类、失败断言、耗时、指标和产物完整性 |

对输入事件记录服务器实际接受的 Tick 和顺序。记录设大小上限，达到上限时明确标记不完整，禁止静默截断后宣称完整复现。

**验收：**关闭原游戏进程后仍可读取记录；不同运行不覆盖产物；凭证和 API Key 不出现在文件中。

### FR-16 历史状态回放

- 可打开一次运行，播放、暂停、调整速度并跳转到选定 Tick 或失败事件。
- 展示服务器历史位置、得分、金币和相关事件；有客户端记录时同时展示其状态。
- 快照间可以为展示而插值，但须区分原始记录点与插值显示，不能据插值生成虚假的逻辑帧证据。
- 缺少客户端数据时明确提示，不重建并冒充真实客户端历史。
- 首版界面明确称“状态回放”；重新执行输入并核对状态哈希属于 P1。

**验收：**用户从失败报告进入对应时刻，并看到相关状态和事件；损坏或不兼容文件给出错误，不崩溃。

### FR-17 结果展示与场景重跑

- 显示场景名称、运行状态、断言统计、失败原因、运行时间和产物位置。
- 提供命令或界面入口，使用保存的配置重跑同一场景。
- 比较两次结果时显示版本与环境差异，不将不同条件下的指标直接归因为修复效果。

**验收：**无需模型服务即可重跑保存场景；用户可对应查看修复前后的失败证据和结果。

## 7. AI 辅助功能

### FR-18 自然语言生成测试场景

- 用户输入测试目标，AI 在已支持的动作和断言集合内生成 JSON 场景。
- 生成结果经过结构和语义校验，界面展示参与者、步骤、网络条件、断言和预计超时。
- 生成与执行是两个明确操作；用户确认场景后才运行。
- 不支持的意图应明确说明限制，不把它改写成无关场景后声称完成。
- 模型输出不能包含执行代码、终端命令、任意文件读写或未授权外部目标。

**验收：**“两人争抢同一金币，其中一人重连并重试拾取”能生成包含相关动作和唯一领取断言的有效配置；未知动作或虚构断言无法通过校验。

### FR-19 模型配置、失败与离线使用

- 模型地址、名称、超时和密钥通过独立配置管理，密钥不进入仓库或场景文件。
- 请求超时、认证失败、限额、非法输出分别提示；不进行无界重试。
- 非法输出允许最多 2 次自动修正，仍失败则保留可查看的错误摘要并停止。
- 用户可修改或直接手写场景；内置场景、游戏和回放不依赖模型。
- 首版只需验证一种模型接入方式，并写明实际测试的配置；不宣称兼容所有供应商。

**验收：**移除模型配置后核心流程仍可使用；调用失败不会影响服务器逻辑帧，也不会自动运行未校验内容。

### FR-20 AI 场景生成评测

- 建立至少 20 条固定测试意图，包含正常请求、边界请求和不支持请求。
- 记录首次结构通过率、修正后通过率、可执行率和语义符合情况；公开分母及失败样例。
- 语义符合检查需要确认关键动作和断言，不能仅凭 JSON 可解析判为成功。
- 不为尚未测量的指标填写百分比；不支持请求的正确拒绝应单独统计。

**验收：**发布前存在可复核评测记录，支持意图和拒绝意图分组报告；模型与配置版本可追溯。

## 8. 非功能需求

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| NFR-01 可构建性 | 固定依赖版本，提供明确构建和启动步骤 | 在干净环境按文档构建；记录验证平台 |
| NFR-02 稳定性 | 4 个客户端连续运行多局，总计 30 分钟，无崩溃和未处理异常 | 日志、退出状态及内存检查；30 分钟不是一局时长 |
| NFR-03 逻辑帧预算 | 在公开的基准环境和四人负载下，Tick 计算耗时 P99 小于 33.3 ms | 至少 3 次各 10 分钟测量，分别报告；同时公布调度间隔、超时次数与负载，不能只报告平均值 |
| NFR-04 资源有界 | 输入、快照、重试、日志和连接均有容量或超时限制 | 超限及反复断连测试；回收后无持续资源增长 |
| NFR-05 自动化 | 核心规则、协议校验、幂等和生命周期有自动检查；内置场景可无人值守执行 | 无模型的 CI 流程运行并保留失败产物 |
| NFR-06 可诊断性 | 运行 ID、比赛标识、玩家标识和 Tick 能贯穿相关记录 | 任意失败断言可关联到输入或状态证据 |
| NFR-07 使用体验 | 预置条件满足后约 10 分钟可启动双客户端演示 | 由非开发者按快速开始试跑并记录阻碍 |
| NFR-08 数据与凭证 | 密钥、恢复凭证不进入公开产物；只收集项目运行所需数据 | 检查示例配置、日志、发布包和失败报告 |
| NFR-09 演示故障隔离 | 故意制造业务错误的开关仅存在于测试构建或独立故障夹具 | 普通发布包无法启用；测试报告明确标注故障模式 |
| NFR-10 可维护性 | 游戏规则、传输、记录和 AI 接入有明确边界 | 核心规则可脱离图形客户端及模型服务测试 |

性能目标是指定基准环境下的发布检查，不是任意硬件保证。后续多房间测试必须区分真人客户端、无图形机器人、连接数和活跃玩家数。

## 9. 核心验收场景

| 编号 | 场景与步骤 | 预期结果 | 对应需求 |
| --- | --- | --- | --- |
| AC-01 | 两人连接、进房、准备、开始、拾取、结算 | 一局完整结束，双方最终得分与服务器一致 | FR-01、03–08 |
| AC-02 | 四人进房后第五人请求加入；单人尝试开始 | 容量及开始条件被正确限制 | FR-03、04 |
| AC-03 | 两玩家同 Tick 拾取同一金币 | 最多一次成功事件，总分仅增加 1 | FR-05、06、13 |
| AC-04 | 发送重复拾取请求；再以新请求序号领取同一金币 | 两种重复均不增加额外得分 | FR-05、06、11–13 |
| AC-05 | 玩家得分后断线，在保留期内重连；旧连接再发消息 | 得分保留、实体唯一、旧连接消息无效 | FR-02、07、09、13 |
| AC-06 | 断线超过保留期后恢复；结算后尝试恢复运行 | 旧实体释放，不能恢复已结束比赛的游戏行为 | FR-04、09 |
| AC-07 | 分别执行正常网络、各方向额外 75 ms 延迟、各方向 3% 丢包 | 无崩溃；权威规则保持；呈现网络条件和校正变化，不要求三次轨迹逐帧相同 | FR-08、10、14 |
| AC-08 | 客户端先接受新快照，再收到旧快照 | 已应用的权威状态不回退 | FR-07、13、14 |
| AC-09 | 测试夹具分别启用重复加分、重连残留实体、旧快照覆盖错误 | 对应断言确实失败；普通正确实现通过同一案例 | FR-13、15–17；NFR-09 |
| AC-10 | 打开 AC-09 产物并跳转至失败事件 | 看到正确来源的状态、事件及期望/实际差异 | FR-15–17 |
| AC-11 | 输入支持和不支持的自然语言目标 | 支持目标生成可校验场景，不支持目标明确反馈 | FR-18–20 |
| AC-12 | 移除模型配置，运行内置场景并查看报告和回放 | 全流程可运行，无隐式模型依赖 | FR-12、15–17、19 |
| AC-13 | 提交畸形协议包、过量输入、未知动作以及损坏回放 | 有界拒绝或清晰错误，不崩溃、不静默通过 | FR-01、06、12、16 |

AC-09 中“故障模式触发预期失败”属于测试自身有效性的验证，不能把故障模式下的 FAIL 计入正常实现的发布通过率。

## 10. 完成定义与后续设计

每项 P0 功能完成须同时满足：行为实现、正常与异常路径验证、必要使用说明、可追溯验收证据。仅在界面出现按钮或日志输出成功不算完成。

配套设计文档已给出模块与接口契约；开发前还需按以下事项完成工程验证和细化，验证结果不得以接口草案代替：

1. C++ 与 Godot 的传输互通验证结果、消息编码和协议版本规则。
2. 线程与 Tick 调度、输入队列边界、迟到输入策略和过载行为。
3. 客户端预测与服务器运动模型的一致性方案。
4. 弱网注入层级、可用平台和隔离方式。
5. 场景 JSON Schema、断言结构、记录格式和版本兼容规则。
6. 编译、发布、CI 和基准环境的具体配置。

这些属于实现设计任务，不改变本说明书已定义的用户行为和验收标准；若验证结果要求改变需求，应先记录对应编号及影响。
